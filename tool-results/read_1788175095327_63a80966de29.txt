   149→[]{#_Toc100003 .anchor}**3.1 How to Upload and Load the Six Documents**
   150→
   151→The six documents are in the Word format, and they must be loaded into
   152→the AI builder\'s context before the build begins. The loading method
   153→depends on the AI builder being used, and the three dominant methods are
   154→the project file upload, the context file, and the paste. For Claude
   155→Code, the documents are placed in the project directory and referenced
   156→in the CLAUDE.md file, which is the context file that Claude Code reads
   157→at the start of every session; the builder creates a CLAUDE.md that
   158→lists the six documents and instructs Claude Code to read the relevant
   159→sections before starting any task. For Cursor, the documents are
   160→uploaded to the project\'s context, or the relevant sections are pasted
   161→into the conversation, or the documents are placed in the project
   162→directory and referenced with the at-file syntax. For OpenAI Codex and
   163→the multi-agent systems, the documents are uploaded as project files or
   164→are loaded through the system\'s document ingestion mechanism.
   165→
   166→The recommended approach, regardless of the AI builder, is to create a
   167→project directory that contains the six documents and a context file
   168→that lists them. The context file, whether it is CLAUDE.md for Claude
   169→Code, AGENTS.md for the multi-agent systems, or the cursor rules for
   170→Cursor, should contain the following: the list of the six documents with
   171→their file paths, the instruction to read the relevant sections before
   172→starting any task, the three-phase model of context loading, analysis,
   173→and implementation, and the verification gate that must be run after
   174→every task. The context file is the entry point that the AI builder
   175→reads first, and it is the file that directs the builder to the six
   176→documents and to the prompt architecture that governs the build.

  1620→[]{#_Toc100020 .anchor}**7. The Build Strategy: Sequencing and
  1621→Verification**
  1622→
  1623→The build strategy is the plan that governs the sequence of prompts and
  1624→the verification of outputs, and it is the strategy that converts the
  1625→prompt templates into a working system. The strategy follows the
  1626→three-phase model from the second document, with the document
  1627→consumption protocol from the fifth document, and it is adapted to the
  1628→specific system being built. This section specifies the strategy, the
  1629→sequencing, and the verification, and it is the section that the builder
  1630→uses to plan the build from the first prompt to the final verification.
  1631→
  1632→[]{#_Toc100021 .anchor}**7.1 The Prompt Sequence**
  1633→
  1634→The prompt sequence is the order in which the builder issues the prompts
  1635→to the AI builder, and it follows the three-phase model. The first
  1636→prompt is the system-specific prompt from the previous sections, which
  1637→directs the AI builder to consume the documents and to produce the
  1638→synthesis. The builder reviews the synthesis, corrects any
  1639→misunderstanding, and approves it. The second prompt directs the AI
  1640→builder to produce the task list, which the builder reviews and
  1641→approves. The subsequent prompts, one per task, direct the AI builder to
  1642→implement each task, to run the verification gate, and to report the
  1643→result. The sequence continues until all tasks are complete and the
  1644→system meets the documented standard.
  1645→
  1646→[]{#_Toc100022 .anchor}**7.2 The Verification Strategy**
  1647→
  1648→The verification strategy is the set of checks that the builder runs
  1649→after each task to verify that the output meets the specification. The
  1650→strategy is documented in the fourth document\'s testing strategy
  1651→section, and it includes the unit tests, the integration tests, the
  1652→end-to-end tests, the contract tests, the security tests, the
  1653→accessibility tests, and the performance tests. The builder does not
  1654→accept a task as complete until the verification gate passes, and the
  1655→builder does not allow the AI builder to proceed past a failed gate. The
  1656→verification is the discipline that ensures the quality of the build,
  1657→and it is the discipline that distinguishes a directed build from an
  1658→undirected generation.
  1659→
  1660→[]{#_Toc100023 .anchor}**7.3 The Failure Handling**
  1661→
  1662→The failure handling is the process that the builder follows when a task
  1663→fails the verification gate, and it follows the graceful degradation
  1664→model from the sixth document. The first response to a failure is the
  1665→retry, where the AI builder is directed to fix the failure and to re-run
  1666→the gate, with a maximum of three retries. If the retry fails, the
  1667→builder escalates, either by taking over the task manually (the solo
  1668→builder takeover) or by re-prompting the AI builder with a more specific
  1669→instruction. If the AI builder is unavailable, the builder continues
  1670→with the solo execution, reading the pending tasks from the shared task
  1671→ledger and implementing them one by one. The failure handling is the
  1672→discipline that ensures the build continues regardless of the failures,
  1673→and it is the discipline that prevents the data loss and the
  1674→work-in-progress loss that a careless failure handling would produce.

  1740→[]{#_Toc100025 .anchor}**8. Counterarguments and Limitations**
  1741→
  1742→The recommendations in this report are subject to several
  1743→counterarguments and limitations. The first counterargument is that the
  1744→prompt templates are too long and too detailed, and that an AI builder
  1745→can produce a working system with a shorter, simpler prompt. This
  1746→argument is valid for a prototype, where the goal is to test an idea
  1747→rather than to build a production system. The argument fails for a
  1748→commercial system, because the detail in the prompt is the detail that
  1749→prevents the AI builder from improvising, from hallucinating components,
  1750→and from producing the AI-flag work that fails the credibility test. The
  1751→prompt length is the investment in the quality of the output, and the
  1752→return on the investment is the difference between a system that meets
  1753→the real-world standard and a system that does not.
  1754→
  1755→The second counterargument is that the system-specific prompts are
  1756→redundant, because the master template can be adapted to any system by
  1757→the builder. This argument has merit, and the master template is indeed
  1758→the foundation. The system-specific prompts are provided because they
  1759→save the builder the effort of adapting the master template for each
  1760→system, and because they ensure that the system-specific content, the
  1761→data model, the process flows, and the constraints, are correctly
  1762→specified. A builder who is familiar with the master template can adapt
  1763→it, but a builder who is starting will benefit from the system-specific
  1764→prompts as the starting points.
  1765→
  1766→The third counterargument is that the advanced combination prompts,
  1767→particularly the Smart School Platform, are too ambitious for a single
  1768→build, and that a builder who attempts them will fail. This argument is
  1769→valid in the sense that the Smart School Platform is a large build, but
  1770→the argument misses the point. The combination prompt is not a single
  1771→build; it is a phased build, with the implementation roadmap specifying
  1772→the phases and the dependencies. The builder executes the phases
  1773→sequentially, with each phase producing a working subset of the
  1774→platform, and the combination prompt is the prompt that directs the
  1775→overall build, not the prompt that builds everything at once. The
  1776→recommendation is to use the combination prompt as the master plan and
  1777→to execute the phases as the individual builds.
  1778→
  1779→A limitation is that the prompt templates are written for the 2026 AI
  1780→builders, and the builders and the models are evolving rapidly. A
  1781→builder using the templates in a later period should verify that the
  1782→recommendations, particularly the stack selection and the tool
  1783→recommendations, are still current, and should adapt the templates to
  1784→the specific capabilities of the builder and the model being used. The
  1785→templates are the starting point, not the final word, and the builder\'s
  1786→judgment is the ultimate guide.

  1788→[]{#_Toc100026 .anchor}**9. Conclusion and Strategic Implications**
  1789→
  1790→The question that opened this report was how a builder takes the six
  1791→documents and uses them with an AI builder to construct the desired
  1792→system, and what to prompt to start the build. The document has provided
  1793→the loading instructions, the master prompt template, the
  1794→system-specific prompts for each of the eight system categories, the
  1795→advanced combination prompts for the integrated platforms, and the build
  1796→strategy that governs the sequencing and the verification. The central
  1797→value is that the document converts the six-document playbook from a
  1798→reference into an actionable sequence of prompts, and it is the document
  1799→that a builder uses at the keyboard to direct the AI builder to produce
  1800→the system.
  1801→
  1802→The strategic implication is that the seven documents, the foundation,
  1803→the prompt guide, the stack guide, the operational excellence guide, the
  1804→scalability guide, the multi-agent guide, and this prompt template
  1805→library, together constitute the complete playbook that a builder uses
  1806→to direct an AI builder to construct a production-grade system. The
  1807→first six documents are the specification; this seventh document is the
  1808→operation. A builder who loads the six documents as context, who uses
  1809→the loading instructions and the context file from this document, and
  1810→who issues the system-specific prompts from this document, will direct
  1811→the AI builder to produce a system that meets the real-world standard,
  1812→that does not exhibit the integration conflicts, that does not fail the
  1813→security audits, and that generates the revenue that justifies the
  1814→build.
  1815→
  1816→The closing recommendation is therefore the following. A builder who
  1817→intends to direct an AI builder to construct a production-grade system
  1818→should place the seven documents in the project directory, should create
  1819→the context file that lists them, should select the system-specific
  1820→prompt that matches the system being built, should adapt the bracketed
  1821→sections to the specific requirements, and should issue the prompt as
  1822→the first message to the AI builder. The builder should follow the
  1823→three-phase model, should review and approve each phase\'s output, and
  1824→should enforce the verification gate after every task. The discipline of
  1825→the seven documents and the prompt architecture is the discipline that
  1826→produces a system that meets the real-world standard, and this document
  1827→is the seventh that makes the playbook actionable.
