   223→[]{#_Toc100003 .anchor}**3.1 Key Definitions**
   224→
   225→Before proceeding, it is necessary to define the key terms. Scalability
   226→is the property of a system to handle increasing load, whether in users,
   227→in requests, or in data volume, without degradation of performance or
   228→reliability, and it is achieved through horizontal scaling, vertical
   229→scaling, caching, and the architectural patterns that this document
   230→specifies. Concurrency control is the discipline of coordinating
   231→simultaneous access to shared data so that conflicts are prevented or
   232→resolved, and it encompasses the optimistic and pessimistic locking
   233→strategies, the distributed locks, and the idempotency patterns. Data
   234→consistency is the property that the data across the system, whether in
   235→a single database or across multiple databases, is correct and coherent,
   236→and it is governed by the consistency model, the transaction isolation
   237→level, and the distributed transaction patterns such as the Saga. A
   238→multi-database architecture, or polyglot persistence, is the pattern of
   239→using different databases for different data characteristics, such as a
   240→relational database for transactional data, a document database for
   241→schema-flexible content, a time-series database for telemetry, and a
   242→graph database for relationships, with coordination across them. A
   243→central data hub is the architectural component that provides a unified,
   244→role-controlled access layer to the sensitive data that multiple
   245→management functions must share, and it is the component that prevents
   246→the data silos that the multi-database pattern can produce.

   491→
   492→Scalability is the property of the system to handle increasing load
   493→without degradation, and it is the property that the user\'s question
   494→about overload and downtime addresses. A system that cannot scale will,
   495→at some load level, become slow, then unresponsive, then unavailable,
   496→and the failure mode is the failure mode that destroys user trust and
   497→that produces the incidents that the SRE discipline must respond to. The
   498→scalability is achieved through a combination of load balancing,
   499→auto-scaling, rate limiting, caching, and the circuit breaker pattern,
   500→and each is a discipline that the AI builder must be directed to
   501→implement. This section covers each discipline with the depth the
   502→builder needs.
   503→
   504→[]{#_Toc100014 .anchor}**5.1 Load Balancing**
   505→
   506→Load balancing is the distribution of incoming traffic across multiple
   507→servers, and it is the discipline that prevents any single server from
   508→becoming the bottleneck. The load balancer is the component that
   509→receives the incoming requests and routes them to the available servers,
   510→using a scheduling algorithm such as round-robin, least-connections, or
   511→IP-hash. The load balancer also performs the health checks that detect
   512→failed servers and that route traffic away from them, and it performs
   513→the SSL termination that offloads the encryption from the application
   514→servers. Practitioner sources report that the load balancer is one of
   515→the most critical components in the path, and that the wrong load
   516→balancer will surface its limitations at the worst time, usually during
   517→an incident. The recommendation for a production system is a managed
   518→load balancer, such as the AWS Application Load Balancer, the Google
   519→Cloud Load Balancer, or the Azure Load Balancer, with Cloudflare or a
   520→comparable content delivery network at the edge for the global traffic
   521→distribution. The AI builder should be directed to provision the load
   522→balancer through the infrastructure-as-code, to configure the health
   523→checks, and to verify the load distribution under load testing.
   524→
   525→[]{#_Toc100015 .anchor}**5.2 Auto-Scaling**
   526→
   527→Auto-scaling is the dynamic adjustment of the number of application
   528→instances in response to the load, and it is the discipline that allows
   529→the system to handle the traffic spikes without over-provisioning for
   530→the average load. The auto-scaling is configured with a scaling policy
   531→that specifies the metric to monitor, such as the CPU utilization or the
   532→request queue depth, the threshold that triggers the scaling, and the
   533→minimum and maximum number of instances. The auto-scaling adds instances
   534→when the metric exceeds the threshold and removes instances when it
   535→falls below, and it does so with a cooldown period to prevent the
   536→thrashing that rapid scaling and de-scaling would produce. The AI
   537→builder should be directed to configure the auto-scaling through the
   538→infrastructure-as-code, to set the scaling policy based on the system\'s
   539→load profile, and to verify the scaling behavior under load testing. The
   540→auto-scaling is the complement to the load balancing, because the load
   541→balancer distributes the traffic and the auto-scaling ensures there are
   542→enough servers to handle it.
   543→
   544→[]{#_Toc100016 .anchor}**5.3 Rate Limiting**
   545→
   546→Rate limiting is the control of the rate at which a client, whether a
   547→user or an API consumer, can submit requests, and it is the discipline
   548→that prevents the abuse, the accidental overload, and the
   549→denial-of-service that a single client can produce. The rate limiting is
   550→implemented at the API gateway or at the load balancer, and it uses a
   551→token bucket or a sliding window algorithm to enforce the limit. The
   552→limit is typically per-client, identified by the IP address or the API
   553→key, and it is set to a level that allows legitimate use while
   554→preventing abuse. The rate limiting returns a 429 Too Many Requests
   555→status when the limit is exceeded, with a Retry-After header that tells
   556→the client when to retry. The AI builder should be directed to implement
   557→the rate limiting at the API gateway, to set the limits based on the
   558→system\'s capacity and the legitimate use patterns, and to verify the
   559→limiting under load testing. The rate limiting is the discipline that
   560→protects the system from the overload that a single client can produce,
   561→and it is the discipline that the user\'s question about overload
   562→directly addresses.
   563→
   564→[]{#_Toc100017 .anchor}**5.4 Caching Strategies**
   565→
   566→Caching is the storage of frequently accessed data in a fast,
   567→low-latency store, and it is the discipline that reduces the database
   568→load and the response latency. The cache is implemented with Redis or a
   569→comparable in-memory store, and it uses one of several strategies: the
   570→cache-aside strategy, where the application reads from the cache and, on
   571→a miss, reads from the database and writes to the cache; the
   572→write-through strategy, where the application writes to the cache and
   573→the cache writes to the database synchronously; and the write-behind
   574→strategy, where the application writes to the cache and the cache writes
   575→to the database asynchronously. The cache-aside is the most common and
   576→the simplest, and it is the recommended starting point. The
   577→write-through and the write-behind are used when the write latency or
   578→the write throughput is a concern. The AI builder should be directed to
   579→implement the caching for the hot-path data, to set the cache expiration
   580→based on the data\'s volatility, and to verify the cache hit rate under
   581→load testing. The caching is the discipline that most reduces the
   582→database load, and it is the discipline that allows the system to handle
   583→the read-heavy workloads that dominate most web applications.
   584→
   585→[]{#_Toc100018 .anchor}**5.5 The Circuit Breaker Pattern**
   586→
   587→The circuit breaker is the pattern that prevents the cascading failure
   588→that occurs when a downstream service fails and the upstream service\'s
   589→requests pile up waiting for the response. The circuit breaker monitors
   590→the failure rate of the calls to the downstream service, and when the
   591→failure rate exceeds a threshold, the circuit opens, and subsequent
   592→calls fail fast rather than waiting. The circuit remains open for a
   593→cooldown period, after which it enters a half-open state, where a
   594→limited number of calls are allowed to test whether the downstream
   595→service has recovered. If the test calls succeed, the circuit closes and
   596→the normal operation resumes; if they fail, the circuit reopens. The
   597→circuit breaker is the pattern that contains the failure to the failing
   598→service and that prevents the failure from propagating to the rest of
   599→the system. The AI builder should be directed to implement the circuit
   600→breaker for the calls to the external services, the payment processors,
   601→the email providers, and the model providers, and to configure the
   602→failure thresholds and the cooldown periods based on the service\'s
   603→reliability.
   604→
   605→[]{#_Toc100019 .anchor}**6. Concurrency Control: Preventing Input
   606→Conflicts and Double Entries**
   607→
   608→Concurrency control is the discipline of coordinating simultaneous
   609→access to shared data so that conflicts are prevented or resolved, and
   610→it is the discipline that the user\'s question about input conflicts and
   611→double entries addresses. The concern is real and is the most common
   612→cause of data corruption in a multi-user system. When two users submit
   613→the same form simultaneously, when a network retry submits the same
   614→request twice, or when a user clicks the submit button multiple times,
   615→the system must prevent the double entry and the data corruption that
   616→would result. The concurrency control is achieved through a combination
   617→of locking strategies, idempotency patterns, and the distributed
   618→transaction patterns, and each is a discipline that the AI builder must
   619→be directed to implement.
   620→
   621→[]{#_Toc100020 .anchor}**6.1 Optimistic Locking**
   622→
   623→Optimistic locking is the strategy that assumes conflicts are rare and
   624→that checks for conflicts at the time of the update rather than locking
   625→the resource upfront. The implementation uses a version field on each
   626→record, and the update includes the version in the WHERE clause, so that
   627→the update succeeds only if the version has not changed since the record
   628→was read. If the update affects zero rows, the application knows that
   629→the record was modified by another process, and it can retry or report
   630→the conflict. Practitioner sources recommend optimistic locking as the
   631→starting point for most concurrency control, because it is the simplest,
   632→requires no extra infrastructure, and scales the best. The AI builder
   633→should be directed to implement the optimistic locking with a version
   634→field on every entity that is subject to concurrent updates, and to
   635→handle the conflict by retrying or by reporting the conflict to the
   636→user.
   637→
   638→[]{#_Toc100021 .anchor}**6.2 Pessimistic Locking**
   639→
   640→Pessimistic locking is the strategy that assumes conflicts are likely
   641→and that locks the resource upfront, before the operation begins, so
   642→that no other process can modify it until the lock is released. The
   643→implementation uses the database\'s SELECT FOR UPDATE statement, which
   644→acquires a row-level lock that is held until the transaction commits or
   645→rolls back. The pessimistic locking is suitable when conflicts are
   646→expected frequently, when the operation is short, and when the cost of a
   647→retry is high. The pessimistic locking has the disadvantage that it can
   648→produce deadlocks, where two transactions each hold a lock that the
   649→other needs, and the database must detect and resolve the deadlock by
   650→aborting one of the transactions. The AI builder should be directed to
   651→use the pessimistic locking selectively, for the operations where the
   652→conflicts are likely and the cost of a retry is high, and to implement
   653→the deadlock detection and the retry.
   654→
   655→[]{#_Toc100022 .anchor}**6.3 Distributed Locks with Redis**
   656→
   657→The distributed lock is the lock that works across multiple application
   658→instances, and it is the lock that is needed when the application runs
   659→on multiple servers and the database\'s row-level lock is not
   660→sufficient. The distributed lock is implemented with Redis, using the
   661→SET NX command to acquire the lock and the DEL command to release it,
   662→with a time-to-live that ensures the lock is released if the holder
   663→crashes. The distributed lock is the pattern that the booking system
   664→uses to prevent two customers from booking the same slot simultaneously,
   665→and it is the pattern that the inventory system uses to prevent two
   666→orders from overselling the last item. Practitioner sources recommend
   667→the Redis SET NX for the general-purpose distributed coordination, with
   668→the Redlock algorithm or the etcd and Consul for the cases where the
   669→strong mutual exclusion guarantees are required, such as the financial
   670→transactions. The AI builder should be directed to implement the
   671→distributed lock for the resources that are subject to concurrent access
   672→across instances, and to handle the lock acquisition failure by retrying
   673→or by reporting the conflict.
   674→
   675→[]{#_Toc100023 .anchor}**6.4 Idempotency: Preventing Double Entries**
   676→
   677→Idempotency is the property that an operation produces the same result
   678→whether it is executed once or multiple times, and it is the property
   679→that prevents the double entries that network retries and user
   680→impatience produce. The implementation uses an idempotency key, a unique
   681→identifier that the client generates and sends with the request, and the
   682→server checks the key before processing the request. If the key has been
   683→seen before, the server returns the cached result of the previous
   684→processing rather than processing the request again; if the key is new,
   685→the server processes the request and caches the result with the key. The
   686→idempotency is the pattern that the e-commerce checkout uses to prevent
   687→a duplicate order when the network retries the payment, and it is the
   688→pattern that the booking system uses to prevent a duplicate booking when
   689→the user clicks the submit button multiple times. The AI builder should
   690→be directed to implement the idempotency for every endpoint that creates
   691→or modifies data, using a unique idempotency key sent by the client, and
   692→to cache the result with the key for the duration that a retry is
   693→possible.

   755→[]{#_Toc100024 .anchor}**6.5 Database Connection Pooling**
   756→
   757→Database connection pooling is the management of the database
   758→connections so that they are reused rather than created and destroyed
   759→for each request, and it is the discipline that prevents the connection
   760→exhaustion that is a common cause of the overload the user is concerned
   761→about. The database connection is expensive to create, and a system that
   762→creates a new connection per request will exhaust the database\'s
   763→connection limit at a moderate load. The connection pool maintains a set
   764→of connections that are reused across requests, and the pool size is
   765→configured to match the database\'s capacity and the application\'s
   766→concurrency. Practitioner sources report that the connection pooling is
   767→not optional at scale, and that this one change can ten-times the
   768→throughput. The AI builder should be directed to configure the
   769→connection pool, to set the pool size based on the database\'s capacity,
   770→and to use a pooler such as PgBouncer for the PostgreSQL systems that
   771→need to scale the connection count beyond the database\'s direct
   772→capacity.
   773→
   774→[]{#_Toc100025 .anchor}**7. Data Consistency Across Services: The Saga
   775→Pattern**
   776→
   777→Data consistency across services is the discipline of maintaining the
   778→correct state of the data when a business transaction spans multiple
   779→services, each with its own database, and it is the discipline that the
   780→multi-database architecture requires. The traditional approach, the
   781→two-phase commit, provides the strong consistency but at the cost of
   782→availability, because all participants must be available for the
   783→transaction to commit. The modern approach, the Saga pattern, provides
   784→the eventual consistency by decomposing the distributed transaction into
   785→a sequence of local transactions, each with a compensating transaction
   786→that undoes the effect if a later step fails. The Saga is the pattern
   787→that the microservices architecture uses to maintain the data
   788→consistency without the two-phase commit\'s availability penalty, and it
   789→is the pattern that the AI builder must be directed to implement for any
   790→business transaction that spans multiple services or multiple databases.
   791→
   792→[]{#_Toc100026 .anchor}**7.1 The Saga Pattern Explained**
   793→
   794→The Saga pattern, as documented by the microservices.io reference and
   795→the Microsoft Azure Architecture Center, decomposes a distributed
   796→transaction into a sequence of local transactions, each executed by a
   797→service, with a compensating transaction for each local transaction. If
   798→a local transaction fails, the Saga executes the compensating
   799→transactions for the local transactions that have already completed, in
   800→the reverse order, to undo the effects. For example, an e-commerce order
   801→Saga might consist of the local transactions: reserve inventory, charge
   802→payment, create shipment. If the create shipment fails, the Saga
   803→executes the compensating transactions: refund payment, release
   804→inventory. The Saga does not provide the isolation that a traditional
   805→transaction provides, because the intermediate states are visible to
   806→other transactions, and the Saga must handle the visibility through the
   807→design of the compensating transactions and through the use of the
   808→optimistic locking or the pessimistic locking where the isolation is
   809→critical.
   810→
   811→[]{#_Toc100027 .anchor}**7.2 Coordination: Choreography Versus
   812→Orchestration**
   813→
   814→The Saga can be coordinated in two ways. The choreography approach has
   815→each service publish an event when it completes its local transaction,
   816→and the next service listens for the event and executes its local
   817→transaction in response. The choreography is decentralized and is
   818→suitable for the simple Sagas with few steps. The orchestration approach
   819→has a central orchestrator that commands each service to execute its
   820→local transaction and that handles the compensation if a step fails. The
   821→orchestration is more explicit and is suitable for the complex Sagas
   822→with many steps, where the choreography would become difficult to
   823→follow. The recommendation for a complex system is the orchestration,
   824→because the orchestrator provides a single place to understand the
   825→Saga\'s flow and to manage the compensation, and because the
   826→orchestrator can be tested and verified as a unit. The AI builder should
   827→be directed to implement the Saga with the orchestration for the complex
   828→business transactions, using a workflow engine or a custom orchestrator,
   829→and to implement the compensating transactions for each step.
   830→
   831→[]{#_Toc100028 .anchor}**7.3 The Outbox Pattern**
   832→
   833→The Outbox pattern is the complement to the Saga that solves the
   834→dual-write problem, the problem of writing to the database and
   835→publishing an event atomically. The dual-write problem arises because
   836→the database commit and the event publication are two separate
   837→operations, and a failure between them leaves the system in an
   838→inconsistent state, with the database updated but the event not
   839→published. The Outbox pattern solves this by writing the event to an
   840→outbox table in the same database transaction as the business data, and
   841→a separate process, the relay, reads the outbox table and publishes the
   842→events to the message broker. The Outbox ensures that the event is
   843→published if and only if the database transaction commits, and it is the
   844→pattern that the Saga\'s choreography and the event-driven architecture
   845→depend on. The AI builder should be directed to implement the Outbox
   846→pattern for every service that publishes events, and to implement the
   847→relay that reads the outbox and publishes the events.
   848→
   849→[]{#_Toc100029 .anchor}**8. Multi-Database Architecture and the Central
   850→Data Hub**
   851→
   852→The multi-database architecture, or polyglot persistence, is the pattern
   853→of using different databases for different data characteristics, and it
   854→is the pattern that the user\'s question about using multiple databases
   855→for each management function addresses. The pattern recognizes that no
   856→single database serves all needs: the transactional data needs the ACID
   857→properties of a relational database; the schema-flexible content needs
   858→the flexibility of a document database; the time-series telemetry needs
   859→the throughput of a time-series database; and the relationship-heavy
   860→data needs the traversal performance of a graph database. The
   861→multi-database architecture uses the right database for each data
   862→characteristic, and it coordinates across them through the patterns of
   863→the previous section. The challenge that the multi-database architecture
   864→introduces is the data silo, the situation where the data is fragmented
   865→across the databases and the management functions cannot access the
   866→integrated view they need. The central data hub is the architectural
   867→component that addresses this challenge, by providing a unified,
   868→role-controlled access layer to the sensitive data that multiple
   869→management functions must share.
   870→
   871→[]{#_Toc100030 .anchor}**8.1 Polyglot Persistence: The Right Database
   872→for Each Data**
   873→
   874→The polyglot persistence pattern assigns each data characteristic to the
   875→database that best serves it. The transactional data, the orders, the
   876→users, the financial records, is stored in the relational database,
   877→PostgreSQL, which provides the ACID properties and the row-level
   878→security. The schema-flexible content, the product catalog with varying
   879→attributes, the user-generated content with varying structure, is stored
   880→in the document database, MongoDB or the PostgreSQL JSONB, depending on
   881→the schema volatility. The time-series telemetry, the application
   882→metrics, the user activity logs, is stored in the time-series database,
   883→ClickHouse or InfluxDB, which provides the high-throughput ingestion and
   884→the efficient aggregation. The relationship-heavy data, the social
   885→graph, the recommendation graph, is stored in the graph database, Neo4j,
   886→which provides the efficient traversal. The search index, the full-text
   887→and the faceted search, is stored in the search engine, Meilisearch or
   888→OpenSearch, which provides the typo tolerance and the relevance ranking.
   889→The cache, the sessions, the hot-path data, is stored in the in-memory
   890→store, Redis, which provides the low latency. The AI builder should be
   891→directed to identify the data characteristics of the system and to
   892→assign each to the appropriate database, with the assignment documented
   893→in the architecture decision record.
   894→
   895→[]{#_Toc100031 .anchor}**8.2 The Central Data Hub**
   896→
   897→The central data hub is the architectural component that provides the
   898→unified, role-controlled access layer to the sensitive data that
   899→multiple management functions must share, and it is the component that
   900→prevents the data silos that the polyglot pattern can produce. The
   901→central data hub is not a single database; it is an access layer,
   902→implemented as an API or a data service, that sits in front of the
   903→sensitive data and that enforces the role-based access control, the
   904→audit logging, and the data governance. The management functions access
   905→the sensitive data through the central data hub, not directly, and the
   906→hub enforces the access policy, logs the access, and provides the
   907→integrated view that the management functions need. The central data hub
   908→is the architectural response to the data mesh principle that the data
   909→should be treated as a product, owned by the teams that generate it, and
   910→accessed through a governed interface. The AI builder should be directed
   911→to implement the central data hub as the access layer for the sensitive
   912→data, with the role-based access control, the audit logging, and the
   913→data governance, and to direct all the management functions\' access
   914→through the hub.
   915→
   916→[]{#_Toc100032 .anchor}**8.3 Role-Based Access Control for Sensitive
   917→Data**
   918→
   919→The role-based access control, abbreviated RBAC, is the mechanism that
   920→governs who can access which data, and it is the mechanism that the
   921→central data hub enforces. The RBAC defines the roles, such as the
   922→administrator, the finance officer, the support agent, and the auditor,
   923→and the permissions that each role has on each data category. The
   924→administrator may have the full access to the user data, the finance
   925→officer may have the access to the financial data, the support agent may
   926→have the limited access to the user data needed for the support, and the
   927→auditor may have the read-only access to the audit logs. The RBAC is
   928→enforced at the central data hub, so that every access to the sensitive
   929→data passes through the control, and the access is logged for the audit.
   930→The RBAC should be complemented by the attribute-based access control,
   931→ABAC, for the finer-grained control, where the access decision depends
   932→on the attributes of the user, the data, and the context, such as the
   933→user\'s location, the data\'s sensitivity, and the time of the access.
   934→The AI builder should be directed to implement the RBAC at the central
   935→data hub, to define the roles and the permissions based on the principle
   936→of least privilege, and to log every access for the audit.
   937→
   938→[]{#_Toc100033 .anchor}**8.4 Data Synchronization Across Databases**
   939→
   940→The data synchronization across the databases is the discipline that
   941→keeps the data consistent when it is stored in multiple databases, and
   942→it is the discipline that the multi-database architecture requires. The
   943→synchronization is implemented through the change data capture, CDC,
   944→which captures the changes to the source database and propagates them to
   945→the target databases, or through the event-driven pattern, where the
   946→source service publishes an event and the target services consume it to
   947→update their databases. The synchronization must handle the eventual
   948→consistency, where the target databases are not immediately consistent
   949→with the source but become consistent over time, and the conflict
   950→resolution, where the same data is updated in multiple databases
   951→simultaneously. The AI builder should be directed to implement the
   952→synchronization through the CDC or the event-driven pattern, to handle
   953→the eventual consistency in the application logic, and to implement the
   954→conflict resolution where the simultaneous updates are possible. The
   955→synchronization is the discipline that makes the multi-database
   956→architecture workable, and it is the discipline that prevents the data
   957→inconsistency that would otherwise result.

   997→[]{#_Toc100034 .anchor}**8.5 The Complete Architecture: Putting It
   998→Together**
   999→
  1000→The complete architecture combines the scalability patterns of Part II,
  1001→the concurrency patterns of Part III, and the multi-database patterns of
  1002→Part IV into a coherent system. The incoming traffic enters through the
  1003→load balancer, which distributes it across the auto-scaled application
  1004→instances, with the rate limiting at the API gateway protecting against
  1005→the abuse. The application instances use the connection pool to access
  1006→the PostgreSQL database, with the Redis cache for the hot-path data and
  1007→the Redis distributed lock for the concurrent resources. The idempotency
  1008→middleware prevents the double entries, and the optimistic locking
  1009→prevents the conflicting updates. The business transactions that span
  1010→multiple services are coordinated through the Saga pattern, with the
  1011→Outbox pattern ensuring the reliable event publication. The data is
  1012→stored across the polyglot databases, with the central data hub
  1013→providing the role-controlled access to the sensitive data. The circuit
  1014→breaker protects the calls to the external services, and the monitoring
  1015→and the alerting, governed by the SRE discipline, detect and respond to
  1016→the incidents. The AI builder should be directed to implement the
  1017→complete architecture, with each component specified, verified, and
  1018→documented, and the result is a system that handles the large user
  1019→loads, prevents the input conflicts, and maintains the data consistency
  1020→across the multi-database architecture.

  1022→[]{#_Toc100035 .anchor}**9. Counterarguments and Limitations**
  1023→
  1024→The recommendations in this report are subject to several
  1025→counterarguments and limitations. The first counterargument is that the
  1026→patterns this document specifies, the distributed locks, the Saga, the
  1027→polyglot persistence, and the central data hub, are excessive for a
  1028→system that is not yet at scale, and that a builder who implements them
  1029→prematurely will incur the complexity without the benefit. This argument
  1030→is valid for the earliest stage of a system, where the simplicity of a
  1031→single database and a single application instance is the right choice.
  1032→The counterargument fails for a system that is intended for commercial
  1033→sale, because the patterns are easier to implement at the design stage
  1034→than to retrofit at the scale stage, and the cost of the retrofit, in
  1035→terms of the migration, the downtime, and the data consistency risks, is
  1036→far higher than the cost of the initial implementation. The
  1037→recommendation is to implement the patterns that the system\'s scale
  1038→trajectory will require, with the understanding that the patterns are
  1039→designed to be implemented at the start and to scale with the system.
  1040→
  1041→The second counterargument is that the multi-database architecture
  1042→introduces the operational complexity that a small team cannot sustain,
  1043→and that a single database, well-tuned, can serve the system\'s needs
  1044→for far longer than the polyglot advocates suggest. This argument has
  1045→merit, and the report acknowledges that the polyglot persistence should
  1046→be adopted selectively, for the data characteristics that genuinely
  1047→benefit from a specialized database, and not for the data that the
  1048→primary database serves well. The recommendation is to start with the
  1049→primary database, PostgreSQL, for the transactional data, and to add the
  1050→specialized databases, the search engine, the cache, the time-series
  1051→database, only when the primary database\'s limitations become apparent.
  1052→The central data hub, however, should be implemented from the start,
  1053→because it is the component that prevents the data silos that the later
  1054→addition of the specialized databases would produce.
  1055→
  1056→The third counterargument is that the document consumption protocol of
  1057→Part I is overhead that slows the build, and that an AI builder can
  1058→produce a working system by prompting directly without the five-phase
  1059→protocol. This argument is valid for a prototype, where the goal is to
  1060→test an idea rather than to build a production system. The argument
  1061→fails for a commercial system, because the cost of the protocol is paid
  1062→once, while the cost of the misunderstanding that the protocol prevents
  1063→is paid repeatedly, in the rework, the defects, and the incidents that a
  1064→misunderstanding produces. The protocol is the discipline that ensures
  1065→the builder\'s understanding, and it is the discipline that the user\'s
  1066→question about the builder\'s proper consumption of the documents
  1067→directly addresses.
  1068→
  1069→A limitation is that the document provides the patterns and the
  1070→recommendations but does not provide the complete implementation, which
  1071→is the work of the AI builder directed by the prompts. The patterns are
  1072→the specification, and the implementation is the execution, and the two
  1073→are distinct. The builder who needs the complete implementation should
  1074→direct the AI builder with the prompts from this document and the prompt
  1075→guide, and should verify the output against the verification gates. The
  1076→document is the specification; the builder and the agent are the
  1077→implementation.
